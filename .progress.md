# Graded Elasticity — Progress Log

This file tracks, in order, the work and decisions behind porting the graded
(spatially-varying) elastic/viscous material capability — originally built on the
`hyperelasticity` branch — onto a clean branch from `master`. Entries are appended in the
order the work happened; earlier entries are not rewritten.

## 0. Starting point

The `hyperelasticity` branch (commits by `eslaght`, with two revert/re-add commits by
Spencer Bryngelson) added, together:
- A reference-map field `ξ` (`eqn_idx%xi`), advected with the flow.
- A hyperelastic (neo-Hookean / Mooney-Rivlin) stress module using `ξ` to build the
  deformation gradient and Cauchy stress.
- A `graded` module (`m_graded.fpp`) that makes `Ca_inv` (renamed from `G`) and `Re`
  spatially varying per fluid, using `ξ` as the spatial coordinate, for **both**
  hypoelasticity and hyperelasticity.

`master` had, in the meantime, removed hyperelasticity entirely as "non-operational"
(commit `e3068ab` / PR #1675: no reference to hyperelasticity remains in `master`'s
`src/`), and separately evolved hypoelasticity's own implementation substantially (see
§3 below). The `hyperelasticity` branch is 18 commits ahead of, and 295 commits behind,
`origin/master` at the time of this work — a merge was assessed and found to produce 28
conflicted files, including a modify/delete conflict on `m_hyperelastic.fpp` itself
(`master` deleted it). A direct merge was not pursued for this reason.

## 1. Hyperelastic Riemann-solver findings (precede the branch decision, carried over)

Investigated while the `hyperelasticity` branch was still the active context, before the
decision to start fresh from `master`:

- **System of equations**: the hyperelastic formulation advects a reference map `ξ`
  (`∂ξ/∂t + v·∇ξ = 0`); the Cauchy stress `τ = (G/J)·dev(B)` (neo-Hookean) is computed
  algebraically each RHS call from `B = F·Fᵗ`, `F = (∇ξ)⁻¹`, via finite differences across
  cells — it is not an independently-evolved, flux-carried conservative variable.
- **Flux/wave-speed gap in the (old) hyperelastic branch**: `m_riemann_solver_hll.fpp` had
  no flux branch at all for hyperelasticity (momentum/energy fell through to the
  non-elastic case); `m_riemann_solver_hllc.fpp` had one only for the `ξ` advection flux.
  Neither carried a stress contribution in momentum/energy, unlike hypoelasticity's
  dedicated branches.
- **Direct wave speed for hyperelasticity** used a constant small-strain correction
  `4·Ca_inv/(3·ρ)`, instead of a state-dependent one. An acoustic-tensor derivation (via
  the Truesdell rate of the Cauchy stress, `τ̊ = (2G)/(3J)·[tr(B)·d − (B:d)·I]`) gives the
  consistent, finite-strain replacement:
  ```
  c²_correction = (2·G)/(3·J·ρ) · (tr(B) − B_nn)
  ```
  which reduces exactly to `4G/(3ρ)` at the undeformed state (`B = I`, `J = 1`) — a
  consistency check that passed. This needs `tr(B)`, `B_nn`, `J` exposed at the interface,
  which the old implementation did not do.
- Bugs found in the old (`eslaght`) implementation, to track and fix once this work
  reaches hyperelasticity again (see §6):
  1. `m_boundary_primitives.fpp`: the reflective BC for `ξ` was gated
     `hyperelasticity .or. graded` on one face only; the other five faces used
     `hyperelasticity` alone (one even carries the author's own `! todo - change?`),
     so a graded-only case got the wrong `ξ` boundary treatment on 5 of 6 faces.
  2. `m_hyperelastic.fpp:118-120`: an unconditional debug `print *` inside the main GPU
     loop.
  3. `m_hyperelastic.fpp:45`: a comment, `! this may be the error`, left unresolved.
  4. `m_graded.fpp`: the sinusoidal and power-law profile branches carry their own
     `change ... — should this even be included` / `change for params` comments.

## 2. Decision: fresh branch from `master`

Rather than merge the diverged `hyperelasticity` branch, a new branch, **`graded-elasticity`**,
was created directly from `origin/master`. Plan, in order:
1. Port the graded capability onto **hypoelasticity** first (this is in progress — see §4).
2. Port graded + the hyperelastic module back in afterward.
3. Return to the hyperelastic Riemann-solver work from §1 (flux consistency, then the
   acoustic-tensor wave speed) once hyperelasticity exists again on this branch.
4. Separately: evaluate upgrading the hyperelastic module's spatial derivative
   (`∇ξ`, currently centered finite differences) to a WENO-based reconstruction. Not
   simple — WENO reconstructs face values from cell averages for a Riemann solver; the
   current gradient is a cell-centered operator with no reconstruction step, so this is a
   design change, not a parameter swap. Deferred until hyperelasticity is back on this
   branch.

## 3. Key finding: `master`'s hypoelasticity has moved on since the branch's fork point

Before porting anything, `master`'s current `m_hypoelastic.fpp` and
`m_riemann_solver_hll.fpp` were read directly (not assumed from the old branch):

- **Naming**: `master` still calls the shear modulus `G` (`fluid_pp(i)%G`). The
  `hyperelasticity` branch had renamed this to `Ca_inv` everywhere. This port keeps
  `master`'s `G` naming rather than reintroducing the rename, to minimize surface area
  against `master`.
- **Architecture**: `master`'s hypoelasticity is more developed than at the branch's fork
  point. It still carries stress as a flux-transported quantity through the Riemann
  solver (`G_L`, `G_R`, `tau_e_L`, `tau_e_R`, via a shared `f_elastic_signal_speed()`
  helper — same role as the old inline `sqrt(...)` expressions, just factored out), but
  it *also* now has a separate stress-rate **source term**, added in `m_rhs.fpp`, computed
  from velocity-gradient finite differences in three places:
  `s_compute_hypoelastic_rhs_finite_diff_per_sweep`, `s_compute_hypoelastic_rhs_iface`,
  and `s_compute_hypoelastic_rhs_axisym_geom_dual_pass` (the last two did not exist on the
  `hyperelasticity` branch's fork point). Per-cell shear modulus for this source term is
  held in `G_K_field` (populated from `Gs_hypo(i) = fluid_pp(i)%G`).
- **Consequence for grading**: a graded `G` needs to reach **both** insertion points —
  the mixture `G` computed in `m_variables_conversion.fpp`
  (`s_convert_to_mixture_variables`, feeding `G_L`/`G_R` into the Riemann solver) and the
  per-cell `G_K_field` consumed by all three RHS source routines above. Missing either one
  would leave grading silently inconsistent between the transport and source parts of the
  same physical stress — exactly the failure mode flagged as the priority to avoid.

**Step 1, completed**: added per-fluid `graded_Re`, `graded_Re_init(1)`/`(2)`,
`graded_Re_end(1)`/`(2)` to `definitions.py`, matching the `hyperelasticity` branch's

**Step 2, partially completed**: the `ξ` reference-map field now exists structurally:
- `eqn_idx%xi` added to `eqn_idx_info` (`m_derived_types.fpp`).
- Allocated in `m_global_parameters_common.fpp`, gated on `graded` alone (hyperelasticity
  is not back on this branch yet), inside the same `model_eqns == 5eq .or. 6eq` guard the
  old branch used — matching its gating exactly. Deliberately **not** ported: the extra
  `+ 1` slot the old branch always reserved past `xi%end` for hyperelastic strain energy.
  That slot is written only by the hyperelastic stress module, which does not exist here;
  reserving it now would be a reservation with nothing to use it.
- Conservative form is `ρξ` (Kamrin et al., JFM 2022 — same citation the old branch used),
  wired into both conversion directions in `m_variables_conversion.fpp`.
- Initial condition in `src/pre_process/m_assign_variables.fpp`: `ξ` set to the cell's own
  physical position at `t=0` (the identity reference map). The old branch's `pre_stress`
  option (a spherical pre-stressed initial `ξ`) was **not** ported — it is a hyperelastic
  initial-condition feature with no bearing on grading itself, and reintroducing it now
  would be scope creep ahead of hyperelasticity actually coming back.
- Boundary conditions in `m_boundary_primitives.fpp`: added consistently to **all six**
  reflective-boundary faces (`graded` gate, flipping only `ξ`'s normal component, same
  treatment velocity's normal momentum component gets). This fixes the bug found in §1.1
  rather than reproducing it — master's current `s_symmetry` subroutine already mirrors
  every field by default and only needs an explicit sign flip for the normal component, so
  the fix was simpler to get right here than it would have been in the old branch's
  structure.
- `ξ` advection flux: **added to `m_riemann_solver_hll.fpp` only.** Read into
  `xi_field_L`/`xi_field_R` from the interface primitive state, and fluxed as `ρvξ`
  (identical form to the existing hypoelastic stress flux immediately above it).

**Not done — `ξ` advection flux is missing from `m_riemann_solver_hllc.fpp` and the HLLD
dual-pass path.** Investigated master's current HLLC solver before attempting this: unlike
HLL's single, relatively simple kernel, HLLC's `s_hllc_riemann_solver` is one 1,700-line
subroutine emitted **twice** via a `#:for HYPO in [True, False]` fypp macro (once
hypoelastic-specialized, once pure-fluid), with explicit per-emission GPU private-variable
lists the file's own comments describe as "pinned... at the GPU register ceiling" and
marked "do not merge." Adding `ξ` here correctly means extending both private-variable
lists and the flux assembly inside that structure without breaking either emission's
kernel naming (the file warns a shared name makes AMD flang launch the wrong kernel). This
is riskier than anything done so far, cannot be compile-checked in this environment (no
`gfortran`), and deserves dedicated, careful attention rather than being folded into this
commit. The old `hyperelasticity` branch did not do this correctly either — it gated its
own HLLC `ξ` flux on `hyperelasticity` alone, never on `graded`, and had no `ξ` flux in HLL
at all, so pure graded (non-hyperelastic) runs there never advected `ξ` under any Riemann
solver. This is now **better** than the old branch (HLL works correctly), but not yet
complete: **until the HLLC/HLLD case is handled, `ξ` only advects when
`riemann_solver = 1` (HLL) is selected. Under HLLC or HLLD, `ξ` stays frozen at its initial
value — grading would track a material point's starting position only, not its current,
convected one.** This needs to be flagged to the user as a known limitation, not silently
left for them to discover.

**Verification**: `./mfc.sh precheck` (format, toolchain lint, source lint — which does
catch forbidden raw-pragma/macro-pattern violations even without a compiler — doc

## 12. Acoustic tensor — standalone derivation script

Added `misc/hyperelastic_acoustic_tensor.py`, a self-contained SymPy script (no MFC
imports, no toolchain dependency) that derives the §1 acoustic-tensor correction from
first principles rather than asserting it:
1. States the neo-Hookean stress `tau = (G/J) dev(B)` and the kinematic identity
   `Bdot = L*B + B*L^T` (true for any motion, not specific to this stress law).
2. Builds the Truesdell rate and **symbolically verifies objectivity** — that it depends
   only on the symmetric part of the velocity gradient, not the spin — before trusting
   the result.
3. Confirms the Truesdell rate collapses to the closed form derived by hand,
   `(2G/3J)[tr(B) d - (B:d) I]`.
4. Substitutes a plane-wave ansatz to extract the full 3x3 acoustic tensor `A(n)`
   (going further than the by-hand derivation, which only solved the longitudinal mode).
5. Checks `A(n)` at the undeformed state against the textbook small-strain values
   (`4G/3` longitudinal, `G` transverse) — both match exactly, symbolically.
6. Recovers the longitudinal correction used in `m_riemann_solver_hll.fpp`,
   `(2G)/(3Jρ)(tr(B) - B_nn)`, and checks it numerically against the general `A(n)`
   result over 20 random (unit `n`, symmetric `B`) samples (symbolic equality needs the
   `|n| = 1` constraint carried through, which isn't worth the algebra to verify this).

Ran it end to end: every assertion (objectivity, small-strain limit, closed-form match)
passes. Ends with a comment on how to extend it to the Mooney-Rivlin law also implemented
in `m_hyperelastic.fpp` (stress depends on `B` and `B²`, needs one extra product-rule term
for `d(B²)/dt`; everything after that is unchanged) — not done, since the question that
prompted this was specifically about the neo-Hookean term already wired into the wave
speed.

Caught by `./mfc.sh precheck`'s spell-check before committing: `J. Comput. Phys.` read as
a typo (`Comput` → `Compute`); spelled out as "Journal of Computational Physics" instead.

**Update**: extended the script to the genuine (two-constant) Mooney-Rivlin law —
`mooney_rivlin()`, run after `main()`. Derives the same way (Truesdell rate, objectivity
check, plane-wave acoustic tensor), checks it reduces exactly to the neo-Hookean result
at `C2 = 0`, and checks the small-strain limit against the classical rubber-elasticity
identity `mu = 2(C1 + C2)`. Along the way, found that `s_Mooney_Rivlin_cauchy_solver` in

## 23. Hyperelasticity module ported; HLL flux consistency implemented

Confirmed and executed on the §21 proposal, starting with HLL only (HLLC/HLLD still
excluded, same as graded/RMT already were).

**Module port.** `m_hyperelastic.fpp` is new: `s_hyperelastic_rmt_stress_update`,
`s_neoHookean_cauchy_solver`, `s_Mooney_Rivlin_cauchy_solver`, module init/finalize,
ported from the `hyperelasticity` branch with the `G`→`Ca_inv` rename applied and the
graded override (`Ca_inv_graded_loc`) wired through the same way the rest of this branch
already does it. Known carried-over defect, left as a comment rather than silently
fixed: `s_Mooney_Rivlin_cauchy_solver` is byte-for-byte the same stress law as
neo-Hookean on the source branch — not a distinct constitutive model. The correct
Mooney-Rivlin stress form is worked out in `misc/hyperelastic_acoustic_tensor.py`'s
`mooney_rivlin()` for whenever this gets revisited. `s_hyperelastic_rmt_stress_update` is
called once per RHS evaluation, after the conservative-to-primitive conversion, and
overwrites `q_cons_vf`/`q_prim_vf`'s stress and energy slots from the current reference
map — this is why hyperelastic stress is excluded from the flux work below.

**New RMT top-level flag.** Per the user's confirmed choice, `rmt` is a new, independent
top-level case parameter. `hyperelasticity = T` now requires `rmt = T`; `graded = T`
requires `rmt = T` (previously it only required `hypoelasticity`); a hypoelastic-only
case that wants graded properties sets `rmt = T` with `hyperelasticity = F`. Enforced in
`check_rmt()`/`check_hyperelasticity()` in `case_validator.py`, which also prohibits
`riemann_solver /= 1` and characteristic BCs under `rmt`, matching the existing
graded-only restriction rather than introducing a second one.

**Two new stashed primitive fields.** `tr(B)` and `J = det(F)` are written by both
Cauchy solvers into two new slots right after the existing strain-energy slot
(`eqn_idx%xi%end+2`, `+3`); `sys_size` increases by 3 under `rmt .and. hyperelasticity`
(was +1, strain energy only). These two scalars are enough for the Riemann solver to
recover the direction-aligned `B_nn` without carrying the full B tensor:
`B_nn = tr(B)/3 + J*tau_nn/Ca_inv`, using the normal stress component hypoelasticity
already reads off `tau_e_L(dir_idx_tau(1))`.

**`m_riemann_solver_hll.fpp` flux consistency.** Momentum-flux and energy-flux branches
that were `if (hypoelasticity) then` are now `if (hypoelasticity .or. hyperelasticity)
then` — the momentum equation only cares about the current stress value, not whether it
came from a rate law or an algebraic function of the deformation gradient, so the same
formula applies unchanged. The stress-flux branch is deliberately left
`hypoelasticity`-only, with a comment explaining why: hyperelastic stress is overwritten
algebraically every RHS call (above), so any flux-divergence contribution to
`q_cons_vf(stress)` would be computed and then discarded before ever being read.

**Direct wave speed.** New `f_hyperelastic_signal_speed(c, Ca_inv, trB, J, tau_nn, rho)`
in `m_riemann_state.fpp`, replacing the flat `4*Ca_inv/(3*rho)` constant with the
finite-strain acoustic-tensor correction from §12/`misc/hyperelastic_acoustic_tensor.py`:
`a = sqrt(max(verysmall, c² + (4*Ca_inv*trB)/(9*J*rho) − (2*tau_nn)/(3*rho)))`. Checked by
hand that this collapses to the old constant at `B = I`, `J = 1`, `tau_nn = 0` — the
small-strain limit — matching the script's own symbolic consistency check.

**Bugs found and fixed while wiring this in** (both pre-existing on `hypergraded`, not
carried over from the `hyperelasticity` branch):
- `dir_idx_tau`/`stress_perm` in `m_riemann_state.fpp` were computed only under
  `hypoelasticity`, so they would be stale/unset for a hyperelasticity-only case even
  though the new wave-speed and flux branches both now depend on them. Broadened to
  `hypoelasticity .or. hyperelasticity`.
- The six reflective boundary-condition stress-flip gates in `m_boundary_primitives.fpp`
  (one per face) were likewise `hypoelasticity`-only, despite hyperelasticity sharing the
  same `eqn_idx%stress` slots and `shear_BC_flip_indices`. Broadened the same way.
- A third graded-completeness gap, beyond the two found in §17: the Riemann solver's own
  interface `Ca_inv_L`/`Ca_inv_R` mixing (`s_compute_hypoelastic_interface_energy`) read
  the static `Ca_invs_rs` table directly, with no graded override, for hypoelasticity
  itself — not only for the new hyperelasticity path. Fixed by adding optional
  `Ca_inv_rs_L`/`Ca_inv_rs_R` parameters there (mirroring `s_compute_interface_reynolds`'s
  existing optional `Res` override) and building one shared graded-override array used by
  both the hypoelasticity and hyperelasticity branches.

- `tensora`/`tensorb` sizing and the `∇ξ` loop (lines ~135-149 of `m_hyperelastic.fpp`)

## 34. Analytical verification of HLLC's existing hypoelastic contact/shear treatment, requested before touching HLLC at all

User flagged that the hypoelastic HLLC contact-wave treatment (which they implemented
themselves) might not be fully correct, especially the shear/tangential part, and asked
for this verified analytically -- plus confirmation that HLL's `ξ` handling actually
computes the full material derivative -- before any HLLC proposal work continues.

**`D(ρξ)/Dt` in HLL, confirmed complete.** Read `m_riemann_solver_hll.fpp`'s `ξ`-flux
block directly: it is the standard two-state HLL numerical flux
(`(s_M*(ρ_R v_R ξ_R) - s_P*(ρ_L v_L ξ_L) + s_M*s_P*(ρ_L ξ_L - ρ_R ξ_R))/(s_M - s_P)`),
structurally identical to the stress flux immediately above it. The transient term
`∂(ρξ)/∂t` is handled the ordinary way, by the RK time integrator advancing
`q_cons_vf(xi)` like any other conserved field; the advective term `∇·(ρvξ)` is this
explicit numerical flux. Both are present -- via the continuity equation, this is exactly
equivalent to `Dξ/Dt = 0` (a material point's reference label never changes), which is
the correct physics. Not a gap.

**HLLC's hypoelastic contact-wave treatment** (`m_riemann_solver_hllc.fpp`, `#:if HYPO`
branch): wrote `misc/hllc_hypoelastic_contact_wave.py` (SymPy) to check it against the
standard two-wave Rankine-Hugoniot derivation (Toro, *Riemann Solvers*, Ch. 10), the same
verification method already used for the acoustic tensor.

- **Normal direction (`s_S`, `pres_tot_star`): confirmed exactly correct.** The
  `pres_tot = pres - tau_nn` substitution for bare pressure throughout the standard HLLC
  momentum relations is exactly the two-wave RH solution, symbolically verified term for
  term. No issue.
- **Tangential direction (`u_t_star`, `tau_nt_star`): found a real inconsistency.**
  `u_t_star` *is* the exact solution of the 2-equation tangential-momentum RH system
  (combining the jump across the left and right acoustic waves) -- no algebra mistake
  there. `tau_nt_star` is **not**: the code's formula
  (`(A_R*tau_nt_R - A_L*tau_nt_L)/(A_R - A_L)`) is a simple mass-flux-weighted average of
  the two states' shear stress with no velocity-coupling term, while the value consistent
  with `u_t_star`'s own derivation is `tau_nt_star = sigma_L + A_L*(v_L - u_t_star)`
  (equivalently from the right side) -- a different, more involved expression that the
  script prints in full. `u_t_star` and `tau_nt_star` do not currently solve the same
  system together.
- **A deeper, structural limitation beyond that specific mismatch.** Even a corrected
  `tau_nt_star` would still only be an approximation: the ansatz (a single tangential
  star pair, continuous across the *whole* region between `s_L` and `s_R`, the same way
  `u*`/`pres_tot*` are) implicitly assumes shear jumps at the acoustic wave speed. But
  hypoelasticity has a genuinely separate shear characteristic at
  `u ± sqrt(Ca_inv/rho)` -- confirmed against `equations.md`'s own description of HLLD's
  shear impedance `C = rho_hat*(G_hat + tau_nn_hat)`, cross-checked in the same script.
  HLLC's 3-wave structure has no mechanism for that fourth/fifth characteristic; HLLD's
  does, which is exactly why the user's own understanding (HLLD correct, HLLC not fully)
  checks out analytically, not just by intuition.

**Does this block the hyperelasticity-on-HLLC plan? No.** Hyperelastic stress is not an
independently flux-transported quantity -- it is slaved algebraically to the deformation
gradient every RHS call (`m_hyperelastic.fpp`) -- so it has no tangential star-state
(`u_t_star`/`tau_nt_star`-style quantity) to compute at all. The only part of this file's
hypoelastic machinery the hyperelasticity extension needs is the normal-direction
`pres_tot`/`s_S` substitution, which is the part verified correct above. The tangential
inconsistency is real and worth fixing, but it is a separate, hypoelasticity-only issue,
not a prerequisite for the hyperelasticity HLLC work.

Script committed to `misc/` alongside `hyperelastic_acoustic_tensor.py`, same standalone-
SymPy convention. Verified with `./mfc.sh precheck` (all 7 checks pass) and by actually
running the script (`python3 misc/hllc_hypoelastic_contact_wave.py`).

## 36. Fixed the student's 1D graded-shear-modulus hypoelastic segfault

User reported a student's 1D shock tube with a graded shear modulus (`Ca_inv`) hypoelastic

**Root cause:** `m_riemann_solver_hll.fpp` declares `xi_field_L`, `xi_field_R` as fixed-size
`real(wp), dimension(3)` locals, populated by `do i = 1, num_dims` (correctly bounded --
only fills indices `1:num_dims`). But both `s_grade_Ca_inv` and `s_grade_Re` are then called
as `s_grade_Ca_inv(xi_field_L(1), xi_field_L(2), xi_field_L(3), ...)` -- **always reading
all 3 components**, regardless of `num_dims`. In 1D, indices 2 and 3 are never written
before this read: they hold whatever was left on the stack from a previous call, not the
zero MFC's own convention uses everywhere else this exact pattern appears (`m_hyperelastic.
fpp`, `m_hypoelastic.fpp`, `m_variables_conversion.fpp` all explicitly do

`m_riemann_solver_hll.fpp`'s `xi_field_L`/`xi_field_R` population loop was the one place
that pattern was missing).

directly into `f_calc_projection`'s `dy*ry`/`dz*rz` terms (`m_graded.fpp`) -- if the stack
garbage happens to be a NaN or signaling-NaN bit pattern (which many debug-mode compiler
flags, e.g. `-finit-real=snan`, deliberately seed uninitialized reals with, specifically to
catch bugs like this one), `NaN * 0` is `NaN`, not `0`, so it does not cancel out even when
the graded profile is purely along x. From there it propagates into `Ca_inv_out`, the
stress update, and the wave-speed calculation, and depending on the platform/compiler can
manifest as exactly the kind of crash reported -- consistent with a 1D graded-`Ca_inv`
hypoelastic case specifically (this code path, `if (graded .and. (hypoelasticity .or.
hyperelasticity))`, only exists in `m_riemann_solver_hll.fpp`, confirmed the only file in
the whole source tree that declares `xi_field_L`/`xi_field_R`, so there's nowhere else this
same bug could be hiding).

**Fix:** added `xi_field_L = 0._wp; xi_field_R = 0._wp` immediately before the `do i = 1,
num_dims` loop that populates them, matching the zero-init convention used everywhere else.

`s_grade_Ca_inv`/`s_grade_Re` without per-element bounds matching `num_dims`) -- `Res_graded_L/R`

## 37. Fixed the Mooney-Rivlin model: a genuine second constitutive law, not a Neo-Hookean copy

User asked for this fixed outright, not just proposed. `hyper_model = 2` had been
byte-for-byte identical to `hyper_model = 1` since the module was ported (§23), flagged
in a comment the whole time but never corrected.

**Derivation and verification first**, extending `misc/hyperelastic_acoustic_tensor.py`
with `mooney_rivlin_implementation_check()` (the continuum-level derivation,
`mooney_rivlin()`, already existed from §23's audit): confirmed, before writing any
Fortran,
1. **`B^-1 = (grad_xi)^T (grad_xi)`** -- since `F = (grad_xi)^-1` (the code's own
   convention), `B^-1 = (F F^T)^-1 = (F^-1)^T F^-1 = grad_xi^T grad_xi`. Not used directly
   in the final implementation (which inverts `B` via its own adjugate/determinant
   instead, since `grad_xi`'s pre-inversion value is no longer available by the time the
   Cauchy solver runs), but confirms the two routes agree and explains why a second
   inversion path wasn't necessary.
2. **I2 = 0.5*(tr(B)^2 - tr(B^2))** matches the textbook sum of principal 2x2 minors.
3. **The component-wise stress split** (subtract trace/3 from diagonal entries only,
   leave off-diagonal entries alone -- the same convention `s_hyperelastic_trace_and_
   deviator` already uses for `dev(B)`) is algebraically identical to the matrix form
   `tau = (1/J)*(2*C1*dev(B) - 2*C2*dev(B^-1))`.
4. **The 1D/2D frozen-direction convention for `tr(B^2)`** (diagonal terms squared,
   off-diagonal terms squared and doubled, plus `(3 - num_dims)` for the frozen unit
   diagonal entries) matches the full 3D embedding -- the same check `plane_strain_
   reduction()` (§28) did for `tr(B)` itself.

All four confirmed symbolically before any Fortran was written.

**Implementation** (`m_hyperelastic.fpp`):
- New per-fluid case parameter `fluid_pp(i)%mr_c2` (Mooney-Rivlin's second material
  constant `C2`; `C1 = Ca_inv/2`, so `Ca_inv = 2*C1` keeps backward-compatible meaning for

  static mixing; grading `C2` independently was not requested and is not supported).
- `B^-1` computed via `B`'s own adjoint/determinant (`det(B) = J**2`) for each of 1D/2D/3D,
  using the same runtime-branch convention established in §31 (not Fypp -- `num_dims` is

- `tr(B^2)` via `2*(sum of all stored components squared) - (sum of diagonal components

## 41. Mooney-Rivlin's direct wave speed: exact C1 term, isotropic-estimate C2 term (Track 2)

Item 2: close the gap §37/§39 flagged (`f_hyperelastic_signal_speed` was Neo-Hookean-only,
missing `mr_c2`'s contribution to the tangent stiffness).

**Derivation** (`misc/hyperelastic_acoustic_tensor.py`'s `mooney_rivlin()`, new Steps 5-6):
repeated `main()`'s own acoustic-tensor derivation (Truesdell rate of the Cauchy stress,
plane-wave substitution, `n.A(n).n` for the longitudinal mode) for the general-B Mooney-
Rivlin stress, this time carrying it through to a GENERAL-B closed form rather than
stopping at the small-strain (`B = I`) check `main()` itself stops at. Result, verified
numerically over 20 random (unit `n`, symmetric `B`) samples to machine precision (both
separately, since the derivation is linear in `C1` and `C2`):

```
rho*c_correction^2 = (4/(3*J)) * [C1*(trB - B_nn) + C2*(5*Binv_nn - trBinv)]
```

The `C1` term exactly matches the already-implemented Neo-Hookean correction (confirms
nothing regressed). The `C2` term's coefficient on `Binv_nn` is 5, not 1 -- NOT a mirror of
the `C1` term's structure, because `B^-1`'s kinematic rate (`-B^-1*Bdot*B^-1`) is genuinely
different from `B`'s own (`L*B + B*L^T`).

**The implementation problem:** `B_nn` is never needed directly -- the existing code
eliminates it exactly via `B_nn = tr(B)/3 + J*tau_nn/Ca_inv`, since `tau_nn` is already an
interface-reconstructed primitive variable (`f_elastic_signal_speed`'s own trick, inherited
by `f_hyperelastic_signal_speed`). `Binv_nn` has no analogous substitution: `tau_nn` is the
SUM of both constants' contributions, not separable into a `C1`-part and `C2`-part without
more information than the interface currently carries, and the full `B^-1` tensor (needed
for its OWN direction-aligned component) is never reconstructed to the interface -- only
scalar invariants (`trB`, `J`) are.

## 44. Retracted the `mu_bulk` proposal: bulk viscosity is already a Reynolds number

The user caught an error in §43's own closing proposal, which suggested "wiring `mu_bulk`
in" as a dimensional viscosity. The code is non-dimensional throughout: `case.md` states it
outright for the non-Newtonian parameters ("all parameters are non-dimensional ... so
`1/mu_eff` equals the local effective Reynolds number"), and `s_compute_mixture_inv_re`'s
own arithmetic confirms it -- the Newtonian path accumulates `alpha(fl)/Res(i,q)` while the
non-Newtonian path accumulates `alpha(fl)*mu_q`, so `mu_q` IS an inverse Reynolds number.
Bulk viscosity therefore already has its proper home: `fluid_pp(i)%Re(2)`, the bulk
Reynolds number. A separate dimensional `mu_bulk` field is redundant with it, and neither
rheology model (Herschel-Bulkley or Carreau-Yasuda) makes the bulk viscosity shear-rate
dependent anyway -- there is nothing for a non-Newtonian-specific bulk parameter to do.

Two further corrections to what §43's answer claimed:
- The current behavior for a non-Newtonian fluid's bulk direction is ZERO bulk viscosity
  (`mu_q = 0._wp` is an inverse viscosity, so zero viscosity / infinite bulk Reynolds
  number), not "effectively infinite bulk viscosity" as stated there.
- That branch is **unreachable dead code**. `Re_idx(2,k)` only lists fluids with
  `fluid_pp(i)%Re(2) > 0`, the default is `dflt_real = -1e6`, and the validator prohibits
  `Re(2)` on a non-Newtonian fluid -- so a non-Newtonian fluid never appears in the bulk
  index list, and the `i == 2` non-Newtonian branch is never entered.

The right change, when someone wants bulk viscosity on a non-Newtonian fluid, is therefore
to let it use `Re(2)` exactly like a Newtonian fluid does (lift the validator prohibition,
delete the vestigial `mu_bulk` field and the dead branch), not to add a dimensional
parameter. Not implemented here -- recorded so the retracted proposal is not picked up
later.

## 48. Automatic CFL now bounds the elastic characteristic speed, for both elastic models

Both models prohibited `cfl_const_dt`/`cfl_adap_dt` for the same reason: the inviscid
time-step candidate is `cfl_target*min_d(dx_d/(|u_d| + c))` with `c` the ACOUSTIC sound
speed, which under-bounds the fastest characteristic whenever elasticity is active, so the
chosen step would be too large. Implemented the fix for both.

**Per-direction, not a scalar worst case.** The elastic stiffening is direction-dependent
in both models -- hypoelasticity through `tau_nn` for the direction in question,
hyperelasticity through `B_nn`/`B^-1_nn` -- so a single isotropic speed would be needlessly
restrictive in some directions and wrong in others. New shared helper
`s_compute_elastic_signal_speeds` (`m_sim_helpers.fpp`) fills a `dimension(3)` array by
calling the same `f_elastic_signal_speed`/`f_hyperelastic_signal_speed` the Riemann solver
uses -- no second copy of either formula, which is the failure mode §45's Bug 4 came from.
It reads the diagonal stress entry at triangular position `d(d+1)/2` for hypoelasticity,
and for hyperelasticity the cell-centered stash `m_hyperelastic.fpp` wrote this same RHS
call, including the per-direction `B`/`B^-1` diagonals added in §43 -- which is precisely
what makes a per-direction bound possible rather than an isotropic fallback. It returns `c`
in every slot when neither model is active, so callers pass the result unconditionally.

`s_compute_dt_from_cfl` and `s_compute_stability_from_dt` take the array as an OPTIONAL
`c_dir` argument (the same pattern `s_compute_interface_reynolds`'s optional `Res` already
uses), so absent it they behave exactly as before. Both the dt path
(`m_time_steppers.fpp`) and both ICFL-diagnostic paths (`m_data_output.fpp`) now pass it --
the diagnostic matters too, since otherwise a user would read a comfortable ICFL off a run
that is actually unstable. `s_compute_cell_state` gained an optional `Ca_inv_K` output (it
already computed the mixture value internally for hypoelasticity and discarded it; now it
computes it for hyperelasticity as well and hands it back on request). The `Rc` cell-
Reynolds diagnostic deliberately keeps the acoustic `c`: it reports viscous-against-
advective scaling, not a wave-speed bound.

## 49. HLLC now supports hyperelasticity

Approved from §48's proposal. The `#:for HYPO in [True, False]` emission in
`m_riemann_solver_hllc.fpp` already carried a complete hypoelastic branch; what it needed was
to become an ELASTIC branch covering either model, with runtime `if (hypoelasticity)` only
where the two genuinely differ.

**What is shared, and why that is sound.** The stress aliases, `pres_tot = pres - tau_nn`, the
contact speed `s_S`, the normal and tangential momentum fluxes and the energy flux are all
common. The tangential star states matter here: `u_t_star` is a velocity, and `tau_nt_star`
IS required (the energy flux uses it for the work of the tangential traction across the wave,
in the `(u_t*tau_nt - u_t_star*tau_nt_star)/(s - u_n)` terms). §38's proposal said
hyperelasticity needs no tangential star state; that was right about the stress EQUATION and
wrong about the energy flux, so it is corrected here. Reusing the hypoelastic relations is
nonetheless correct rather than expedient: they solve the tangential-momentum Rankine-Hugoniot
jump, whose flux is `rho*u_n*v - sigma`, a CONSERVATION statement that holds whatever
constitutes sigma. The constitutive law fixes what `tau_nt` is in each state, not how it jumps
across a wave. `misc/hllc_hypoelastic_contact_wave.py`'s docstring now records this and the one
approximation it carries: the star-state stress is not re-derived from a star-state deformation
gradient, since HLLC constructs no such state -- inherent to applying a contact-wave solver to
a slaved-stress model, and the same compromise HLL's two-state average already makes.

**What differs.** The interface energy correction is hypoelastic-only (hyperelasticity already
took its strain energy out of the pressure upstream), which also means the mixture modulus has
to be mixed directly rather than collected from `s_compute_hypoelastic_interface_energy`'s
`intent(out)`; the wave speed calls `f_hyperelastic_signal_speed` with the stash reads and the
`Ca_inv`/`Ca_inv_2` mixtures; and the stress-EQUATION fluxes plus the cylindrical hoop flux are
skipped, for the reason HLL's own guard already gives.

**Found while implementing: HLLC never advected the reference map at all.** `m_riemann_solver_hll.fpp`
fluxes `rho*xi` explicitly under `if (rmt)`; HLLC had no such flux. Hyperelasticity in HLLC
would have run with a frozen reference map -- no deformation ever developing, the stress stuck
at its initial value -- and graded properties in HLLC were being evaluated at a frozen `xi`
too, which was already wrong before this change. Added, in the shared region next to the
partial-density fluxes whose form it takes exactly (`rho*xi` is advected like `alpha_i*rho_i`),
so both emissions get it and the pre-existing graded case is fixed as well.

**Also closed a second silent-fallback hole the same question surfaced:** nothing stopped
`graded` from running under a non-HLL solver, and only HLL threads the graded overrides
(`Res_graded_L/R`, `Ca_inv_rs_graded_L/R`) through to the interface state -- the others call
the same routines without those optional tables and would quietly use the static per-fluid
values. Now prohibited. `check_hyperelasticity()`'s own solver prohibition relaxes from
HLL-only to HLL-or-HLLC.

Verified by Fypp-expanding `m_riemann_solver_hllc.fpp` and checking the expansion counts
(12 hyperelastic wave-speed calls = 4 per direction; the reference-map flux in both emissions;
the two runtime `hypoelasticity` guards per direction), re-running
`misc/hllc_hypoelastic_contact_wave.py` (all checks still 0), and `./mfc.sh precheck`/`lint`
(966 passed, 1 failed -- the same pre-existing `test_deps_cache.py` failure). No Fortran
compiler here, so this is reviewed rather than compiled or run; a hyperelastic case under
`riemann_solver = 2` compared against `riemann_solver = 1` is the obvious first check.

## 51. Hyperelasticity now works with phase change: dedicated stash indices, then an excluded-energy handoff

Three features could not be used together: `hyperelasticity`, `relax` (phase change) and `amr`.
Nothing prohibited the combination, so it was reachable and silently wrong.

### The defect

`q_cons_vf(E)` adds up three things: kinetic energy, thermal energy, and -- under
hyperelasticity -- the elastic strain energy `W`. That convention is deliberate and the flux
form matches it: `m_riemann_solver_hll.fpp` uses the corrected pressure in `E + pres` and
subtracts the stress power `tau.u`, which is the conservative form for a solid.
`m_hyperelastic.fpp` stashes `W` and takes `W/gamma` back out of the pressure;
`m_variables_conversion.fpp` adds `W` back to `E`. The two are exact inverses.

`m_phase_change.fpp:120` computes `rhoe = q_cons_vf(E) - dynE` and hands it to the pT/pTg
Newton solves, which invert it against a purely thermal stiffened-gas EOS. With
hyperelasticity active that `rhoe` carries `W`, so the solve reports too high an internal
energy and boils phase that must not boil. `eqn_idx%E` appears exactly once in that module,
as a read, so `E` itself is never written -- the misread is the whole defect on that side.

The solver also writes every volume fraction, and `Ca_inv_local` is alpha-weighted, so `W`
changes behind the correction's back. That is *not* a conservation error: `E` is held fixed,
so the strain energy a vaporising phase gives up becomes heat on the next conversion, which
is the intended physics, and `W` falls as the phase disappears so the thermal energy rises --
the error direction cannot produce a negative internal energy. It is a first-order splitting
error of the same character as the relaxation's own split from the RK step, and relaxation is
reapplied every step, so it decays rather than accumulating. An earlier draft of this section
proposed folding `W(p,T)` into the Newton residual to close it exactly; that was overstated
and is not implemented. The closed form stands if exact one-step pT equilibrium is ever
wanted: `W = Ca_inv_local*g1 + Ca_inv_2_local*g2` with `g1 = 0.5*(trB - 3)/J` and
`g2 = (J*J*trBinv - 3)/J`, both already in the stash, and `alpha_i = m_i/rho_i(p,T)` already
produced by the solve.

### Dedicated stash indices (prerequisite)

The stash was addressed as `eqn_idx%xi%end + <literal>` at 52 sites across six files, with
each slot's meaning living only in a comment, and the range expression
`xi%end + 4 + 2*num_dims` written out three times in `m_time_steppers.fpp` alone (the
allocate, seed and deallocate loops). Any field inserted between `xi%end` and the stash would
have shifted all of them silently.

`eqn_idx_info` now carries `elastic_W`, `trB`, `Jdet`, `trBinv` and the `Bdiag`/`Binvdiag`
bounds. `m_global_parameters_common.fpp` assigns them and `sys_size` follows from the last
one, the same pattern `xi` already used, so the arithmetic disappears instead of moving. The
three duplicated range expressions collapse to `eqn_idx%elastic_W, eqn_idx%Binvdiag%end`.
`eqn_idx` is one `GPU_DECLARE` struct with no allocatables and is pushed to the device whole,
so the new members need no separate mapping.

The stash deliberately stays inside `sys_size`. That placement is load-bearing:
`amr_scr_prim` is allocated `1:sys_size` (`m_amr_state.fpp:546`), which is why the AMR path
below needs no new array and no new device map.

### The handoff

`s_infinite_relaxation_k` gained one optional argument, `e_excl`, and one guarded line. The
name is deliberately generic -- "energy the caller excludes from the thermodynamic balance" --
not elastic-specific, because the latent-heat reservoir will need the same exclusion.
`present()` inside a `GPU_PARALLEL_LOOP` has precedent at `m_boundary_common.fpp:187`.

`s_hyperelastic_refresh_stash` repeats the sequence `s_compute_rhs` uses (convert, fill the
primitive buffers the reference-map stencil reads, stress update) and adds no state of its
own. It exists because the stash is recomputed per RHS call, so after a completed step it
describes the last RHS stage rather than the updated state.

- Coarse grid (`m_start_up.fpp`): refresh against `q_prim_qp%vf`, then pass
  `q_prim_qp%vf(eqn_idx%elastic_W)`. `q_prim_qp` was already public from `m_rhs.fpp:52`.
- AMR fine blocks (`s_amr_relax_fine`): the fine blocks already run the full `s_compute_rhs`
  (`m_amr_advance.fpp:201`) with `amr_scr_prim` as the primitive array, so the stash is
  already computed and mapped there. The only problem was *which* block's values sat in that
  shared scratch at relax time -- the RHS is batched and each member lives at a slab offset.
  The refresh runs inside the block frame with `ibounds = idwbuff` and `skip_bc = .true.`, so
  the ghosts come from `amr_cons_br` (loaded with its own ghost shell by `s_amr_br_load`)
  rather than from whichever block last used the scratch, and no boundary-condition or MPI
  work is attempted on a block frame. Those ghosts are one update old, leaving an `O(dt)`
  stash error in each block's outermost interior ring and none elsewhere.
- Pre-process: nothing needed. `m_assign_variables.fpp:344-348` seeds the reference map to
  each cell's own coordinate, so `F = I`, `J = 1` and `W` is identically zero. A pre-strained
  initial condition cannot be prescribed there, and a restart goes through the simulation path.

No prohibition was added or lifted. All three features now work together.

### A separate pre-existing defect, fixed

`s_hyperelastic_rmt_stress_update` loops `j = 0..m, k = 0..n, l = 0..p` -- interior only --
and `m_rhs.fpp` filled the buffers *before* it. So the ghost ring kept an uncorrected
pressure, too high by `W/gamma`, plus a Cauchy stress and stash one RHS call old, and the
reconstruction reads exactly those cells at a domain boundary. At a periodic or reflective
boundary the ghost is a copy of an interior cell, so the error is the full size of the
pressure correction, not a small one. `m_rhs.fpp` now fills the buffers again after the
stress update.

The cost is honest and worth stating: that is a second full ghost fill plus MPI exchange per
RHS stage whenever hyperelasticity is on. A cheaper fix exists -- a flip-aware subset fill for
just the pressure, stress and stash fields, since `s_populate_scalar_buffers` already handles
even scalars but the stress components flip -- and was not taken, because it would duplicate
the flip logic that lives inside `s_populate_variables_buffers`.

### Verification

No Fortran compiler exists here, so item 0 was verified as a pure rename rather than reasoned
about: every touched file was expanded with Fypp using the exact `cmake/Fypp.cmake` flags,
before and after, and the expansions are **identical** once the index names are canonicalised
to a common spelling, comments are stripped and continuation lines are joined. Two files
(`m_global_parameters_common.fpp`, both `m_start_up.fpp`) cannot be expanded without a build
tree -- they include build-generated files -- and that failure reproduces at `HEAD`.

`misc/hyperelastic_stash_indices.py` checks the index arithmetic numerically: for every
`num_dims`, the dedicated indices reproduce the former offsets slot for slot, `sys_size` is
unchanged, the stash is contiguous, it starts one past `xi%end`, and the single
allocate/seed/deallocate bound covers every slot.

`./mfc.sh precheck`: formatting, spell, source lint, doc references, parameter docs and
example cases all pass; the toolchain-lint step fails only on the pre-existing
`test_deps_cache.py::test_a_copy_that_fails_publishes_nothing` (966 passed with it deselected).

What is *not* verified: nothing has been run. The energy handoff, the AMR block frame and the
second buffer fill are all reasoned from the code, not observed. A build with
`-fcheck=bounds` and a hyperelasticity-plus-`relax` case is the natural next step, and a
three-way case with `amr` after that -- no test covers the combination today.

## 52. Audit of the branch against master: three real defects, all of one kind

A sweep of the ~2300 lines this branch adds over `origin/master`, looking for segfaults,
missing calls, allocation and GPU-mapping gaps, hangs and unused variables. Three defects
turned up. All three are the same kind: the hyperelastic stash is a primitive-only field
group, so nothing in the conversion path initialises or refreshes it, and three consumers
assumed somebody else had.

### Defect 1: the array the RHS actually uses was never seeded

`m_time_steppers.fpp` seeds its `q_prim_vf` stash at allocation, with a comment saying why:
without it "the first step reconstructs ghost-cell interfaces from uninitialized memory --
and the wave speed divides by the stashed J".

But `q_prim_vf` is not the array the RHS uses. `m_rhs.fpp` allocates its own `q_prim_qp%vf`
over `eqn_idx%adv%end + 1 .. sys_size`, stash included, and that is the array
`s_hyperelastic_rmt_stress_update` writes, `s_populate_variables_buffers` fills and the
reconstruction reads. It was never seeded. `s_compute_rhs` copies back into the caller's
`q_prim_vf` only over `copy_beg..copy_end`, which is the whole of `sys_size` just when
`probe_wrt`, `ib`, `euler_lagrange`, `synthetic_turbulence` or `run_time_info` is on, and a
zero-trip range otherwise. So the seed protected the wrong array.

### Defect 2: the AMR advance scratch was never seeded

`s_amr_scr_init` allocates `amr_scr_prim(i)%sf` for all of `sys_size`, stash included, and
only allocates. `s_amr_swap_to_fine(widen=.true.)` widens `idwint` but leaves `m`, `n`, `p`
at the block's extents, so the stress update's `j = 0..m` loop covers the block interior and
not the ghost shells. A fine block's ghost ring was therefore reconstructed from
uninitialised memory on the first advance, with the same division by the stashed `J`.
`amr_scr_prim_blk` has the same gap where it is allocated.

### Defect 3: the automatic-CFL elastic bound never saw the deformation

This one is a silent wrong answer rather than a crash, and it defeated §48 and §50 entirely
for hyperelasticity.

`s_compute_dt` converts `q_cons_ts(1)%vf` into `q_prim_vf` itself and then calls
`s_compute_elastic_signal_speeds(q_prim_vf, ...)`, which reads `trB`, `J`, `trBinv` and the
direction-aligned diagonals from the stash. The conversion does not write the stash, and the
RHS copy-back that would have supplied it is the zero-trip range above in any run without
probes, IB, Lagrange particles, synthetic turbulence or `run_time_info`. So the stash stayed
at the allocation-time reference state `B = I`, `J = 1`, `trB = 3` for the whole run, and the
elastic term reduced to a constant stiffening

    a = sqrt(c^2 + 4*Ca_inv/(3*rho) + 8*Ca_inv_2/(3*rho))

instead of the state-dependent speed. A stiffening material's true speed exceeds that, so the
bound was too loose in exactly the regime it exists for. Hypoelasticity was unaffected: its
stress is a transported variable the conversion does write.

### The fix

The seed existed once, inline, in `m_time_steppers.fpp`. It is now
`s_hyperelastic_seed_stash` in `m_hyperelastic.fpp`, called from the two non-AMR places that
allocate a primitive array carrying the stash -- the time stepper, and `m_rhs.fpp` after
`q_prim_qp` is set up -- so one copy of the reference state serves both.

**Defect 2 was reported first and fixed in §55.** It was re-checked against master after the
§53 merge and stood: master changed nothing in `s_amr_scr_init`, which still only allocates,
and `s_amr_swap_to_fine(widen=.true.)` still widens `idwint` while leaving `m`, `n`, `p` at the
block extents, so the stress update covers the block interior only. AMR plus hyperelasticity
therefore read an uninitialised stash ghost ring on the first fine advance. Defect 3 is fixed by having `s_compute_dt` call
`s_hyperelastic_refresh_stash` (added in §51) in place of the bare conversion when
hyperelasticity is on, which rebuilds the stash from the state the bound is about to judge.
All three call sites run after `eqn_idx` is final: global parameters initialise at
`m_start_up.fpp:914`, the RHS module at 957, the time steppers at 965 and AMR at 1017.

The cost of the defect-3 fix is one buffer fill, with its MPI exchange, per dt evaluation --
once per step under `cfl_adap_dt`. The buffer fill is needed because the reference-map
gradient stencil reads xi in the ghost cells, and `s_compute_dt`'s conversion covers `idwint`
only.

### Audited and clean

- **Allocations.** All 37 allocatables the branch adds pair an `@:ALLOCATE`, a

- **Kernel privatisation.** Checked on the *expanded* Fortran, because the private lists are

- **Hangs.** The branch adds no MPI collective and no unbounded loop. The AMR relax loop
  added in §51 iterates `amr_n_my`, which differs per rank, so a collective inside it would

  `s_hyperelastic_rmt_stress_update` contain none, and `s_populate_variables_buffers`, which

- **Cray traps.** Eleven device routines in branch code contain a `GPU_LOOP`; every call site

- **Missing calls.** `m_graded`'s initialise and finalise are wired in all three targets.

## 54. Made the deps-cache test skip under root, so precheck can pass in a container

`test_a_copy_that_fails_publishes_nothing` makes a dependency library unreadable with
`chmod(0)` and asserts that `deps_cache_save` notices it cannot read the file and publishes
nothing. root holds the DAC-override capability and reads a regular file whatever its
permission bits say, so as root the `chmod` never establishes the test's precondition: the copy
in `.github/scripts/deps-cache.sh` succeeds, the entry is published, and the assertion fails.

That failure carries no information about the code under test, and it made `./mfc.sh precheck`
fail for every commit made in a root container -- which is what every commit in this session
had been hitting, forcing the documented `--no-verify` bypass each time. The test now skips in
that case with the reason recorded. Coverage is unchanged where it counts: CI runs
unprivileged, so the test still runs and still guards the behaviour there. `os.name` is tested
first because `os.geteuid` does not exist on Windows.

With this in place precheck passes all seven stages in this container, and the commits for
§52 and §53 were made with the hook running normally rather than bypassed.


## 55. Closed the AMR half of the stash-seeding defect

`m_amr.fpp` now calls `s_hyperelastic_seed_stash` on `amr_scr_prim` immediately after
`s_amr_scr_init`, and on `amr_scr_prim_blk` under the same `ib .or. synthetic_turbulence`
condition that allocates it. That is the whole fix: the shared seeding routine already existed
from §52, so this adds a call and no new state.

Why it is needed, restated from §52: `s_amr_scr_init` allocates `amr_scr_prim(i)%sf` across the
whole of `sys_size`, stash slots included, and only allocates -- `@:ALLOCATE` maps device memory
with `create`, not `copyin`, so neither the host nor the device copy is initialised. The stash
has no conservative counterpart, so no conversion writes it, and
`s_hyperelastic_rmt_stress_update` writes the frame interior only: `s_amr_swap_to_fine(widen)`
widens `idwint` but leaves `m`, `n`, `p` at the block's extents, so the update's `j = 0..m` loop
never reaches the ghost shells. The reconstruction then reads those ghosts and the wave speed
divides by the stashed `J`.

Checked on the way in: `m_amr` can depend on `m_hyperelastic` without a cycle, since
`m_hyperelastic` reaches only `m_derived_types`, `m_global_parameters`,
`m_variables_conversion`, `m_finite_differences`, `m_graded` and `m_boundary_common`, none of
which reach `m_amr` -- and `m_amr_frame` already depends on `m_hyperelastic` for the
finite-difference coefficient rebuild. `eqn_idx` is final well before
`s_initialize_amr_module`: global parameters initialise at `m_start_up.fpp:914` and this module
at 1017. The `amr_scr_prim_blk` guard is the same expression as its allocation at
`m_amr_state.fpp:566`, so the call cannot touch an unallocated array.

All three defects from §52 are now fixed. Verified with Fypp expansion and
`./mfc.sh precheck`, which passes all seven stages. Still not run: a build with
`-finit-real=snan` and `-fcheck=bounds` on an AMR plus hyperelasticity case would confirm the
uninitialised read directly, and no test covers that combination.
